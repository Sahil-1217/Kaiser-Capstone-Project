Two scoring windows are reported separately. The intake model uses only what is known the moment a member makes contact, so it can be deployed as an early warning. Reporting a single figure without saying which window it belongs to would make an undeployable model look like the better one.

How the assistant would work

Retrieval flow

The clinical check runs before retrieval, not after, so no clinical question can be answered out of a policy document.

1 · Symptom checkAcute symptom language routes straight to emergency guidance. Nothing proceeds.
2 · Account-specific checkClaim status and balances need member records, so they route to the portal or an agent.
3 · RetrievePolicy corpus chunked and indexed. Top passages returned with their document and section.
4 · Confidence gateSimilarity below the threshold hands off to a live agent instead of answering.
5 · Draft with citationsEvery factual sentence tied to a retrieved passage.
6 · Grounding checkUngrounded sentences suppress the answer. Pass and fail counts must reconcile with the audit log.
7 · RespondAnswer, sources, and a route to a human on every reply.

The knowledge corpus is published policy documentation, never call transcripts. A transcript records what an agent happened to say, including when they were wrong, and grounding a member-facing assistant in them turns one agent's error into cited policy. Transcripts are used only to decide which questions are worth answering.

Documented assumptions

Gaps in the brief, recorded rather than silently corrected.

  • The brief lists no key field on the service performance, operations or transcript datasets. As written they cannot be joined to anything, so Interaction_ID is carried on all three and Member_ID on interaction history.
  • All data is synthetic, generated with a documented causal structure. The relationships found are real within this dataset; they are not findings about Kaiser Permanente.
  • Negative handle times and out-of-range satisfaction scores are set to unknown rather than corrected, because there is no basis for guessing the intended value.

Feature engineering and leakage control

Why the friction index is built twice

The brief asks for a Service Friction Index combining repeat contacts, escalations and long handle times, and separately asks for a model predicting escalation. Feeding an escalation-based feature into a model predicting escalation hands it the answer and produces an accuracy figure that means nothing.

Two versions are therefore built. The reporting index uses the full record and drives segmentation and the dashboard. The modelling index uses only prior interactions, computed as an expanding window shifted by one, so at any row it reflects that member's earlier history and nothing from the interaction being predicted. Only the second reaches the model.

A correlation check runs over every model feature as a guard rail. It is necessary but not sufficient: Total_Contacts passes a correlation threshold comfortably, yet at the moment a contact arrives nobody knows how many contacts the issue will take. That defect is temporal rather than statistical, which is why the intake and in-flight windows are reported separately on page 3.
